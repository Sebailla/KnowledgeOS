# Documentation Standards

**Project:** KnowledgeOS  
**Section:** Governance  
**Document:** DocumentationStandards  
**Version:** 4.0  
**Status:** Release Candidate  
**Author:** KnowledgeOS Team  

---

## 1. Purpose

Define architecture-document structure, language, formatting, versioning and quality requirements.

## 2. Metadata

Every normative document SHALL include Project, Section, Document, Version, Status and Author.

## 3. Recommended Sections

Purpose, Scope, Normative Language, Responsibilities, Conceptual Model, Requirements, Invariants, Failure and Recovery, Security and Privacy, Examples, Compatibility, Related Documents and Status.

## 4. Normative Language

Use MUST/SHALL for requirements, MUST NOT/SHALL NOT for prohibitions, SHOULD for strong recommendations and MAY for options. Stable rule identifiers SHOULD be used.

## 5. Style

Documents SHALL be precise, explicit about authority/lifecycle/failure, technology-independent at Domain level and free from duplicated definitions.

## 6. References

Relative references SHALL resolve. One document owns each major concept. Other documents reference rather than redefine it.

## 7. Versioning

Patch is clarification, minor is backward-compatible extension and major is breaking semantic or structural change.

## 8. Status Values

Draft, Review, Release Candidate, Approved, Deprecated, Superseded and Archived.

## 9. Diagrams

Diagrams SHALL use official vocabulary, match current architecture, identify scope/level, compile successfully and reference source documents.
